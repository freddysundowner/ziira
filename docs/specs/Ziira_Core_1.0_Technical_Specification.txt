01 · ARCHITECTURE
Architecture
Ziira Core is a multi-tenant web application built as a small kernel with pluggable
modules and plugins: one deployable backend, one primary database, an event bus, and
separate clients for web, point of sale and WhatsApp.

Why one backend with pluggable modules
The modules share one ledger and one stock ledger, and most operations touch several modules in
one database transaction (a sale updates stock, payments and the books together). A monolith
keeps these atomic.
One deployment is simpler to build, test and operate for a small team.
Modules communicate only through public interfaces and events, never by reading each other's
tables, so any module can be enabled, disabled or replaced without changing the others (section
02).

A module cannot be disabled while an enabled module requires it. Optional features switch on or off
automatically when the other module is enabled or disabled.
How units talk to each other
Public interface: each unit exposes a small public.py of functions and data types. Other units may
call only these, never internal code or tables.
In-transaction events: when a document is posted, the kernel dispatches its event to enabled
subscribers inside the same database transaction. This is how Finance posts journals and Inventory
moves stock for a sale, atomically. If Finance is not enabled, there is no subscriber and the sale still
posts.

After-commit events: events are also written to the outbox and processed after commit, for

Step What the kernel does
Install Verifies signature and SDK compatibility, checks dependencies, runs the unit's migrations,

Enable Per tenant: checks required modules are enabled, seeds default data (accounts, reason

Rules for plugins
Plugins use only the published SDK. They never import module internals or write to module tables
directly.
A plugin's tables live in its own PostgreSQL schema ( plg_<name> ) and are created and removed by
its own migrations.
A plugin requests permissions in its manifest; the tenant admin sees and approves them when
enabling.
Hooks run with time limits. A failing after-commit hook is logged and retried, and never breaks the
core operation. Only validation hooks may block an operation.
In 1.0, only plugins built and signed by Ziira can be installed. Third-party plugins can be opened
later with a review process.

Coding standards
Type hints on every function; mypy in strict mode. Ruff for style and formatting.

unit's internals.
Clear names over short names: post_stock_adjustment() , not proc_adj() .

04 · TENANCY
Tenancy and organisation model
Every customer is a tenant. All tenants share the same application and database; every
row belongs to exactly one tenant and is isolated by the database itself.
Tenant (the customer account, billing)
└─ Company (legal entity: KRA PIN, VAT status, chart of accounts, fiscal year)
└─ Branch (outlet: address, eTIMS device, M-Pesa numbers, cash accounts)
└─ Location (store, warehouse, shelf area, in-transit)
Users belong to the tenant and are granted roles per company and branch.
Isolation
Every tenant-owned table has a tenant_id column. PostgreSQL row-level security policies restrict
every query to the tenant set on the connection, so a missing filter in code cannot leak data.

The tenant is resolved from the authenticated session or API key, never from a request parameter.
Background jobs carry the tenant context explicitly and set it before touching data.
Large tenants can later be moved to a dedicated database without code changes, because tenant
context is already explicit.

05 · DATA CONVENTIONS
Data conventions
These rules apply to every table and document. They make the data reliable for
accounting, auditable, and ready for Ziira Intelligence.
Rule Implementation
Database schemas Each unit owns one PostgreSQL schema, e.g. inventory . All tables and columns
are listed in Appendix A.
Identifiers UUID v7 primary keys (time-ordered). Human document numbers are separate,
e.g. INV-THK-2026-000123 .
Standard columns tenant_id , company_id , branch_id , created_at , created_by , updated_at ,
updated_by , source (web, pos, api, import, whatsapp, system), status .
Time Stored in UTC; displayed in Africa/Nairobi. Business date stored separately from
timestamp for documents.
Money numeric(18,2) for amounts, numeric(18,6) for unit costs and rates. No floating
point. Rounding rules defined once.
Status machines Each document type has an explicit set of states and allowed transitions, enforced
in one place.
Posted documents are
immutable
Once a document is posted (affects stock or books), it is never edited. Corrections
are made by a reversing or adjusting document linked to the original.
Ziira Core 1.0 Technical Specification · Confidential Page 8
No hard deletes Drafts may be discarded; anything posted is cancelled or voided, keeping the
record and the reason.
Reason codes Voids, refunds, discounts above policy, price overrides, stock adjustments and
write-offs require a reason code from a managed list, plus optional note.
Creator and approver Stored separately ( created_by , approved_by , approved_at ). The same user
cannot be both where policy forbids it.
External references Payments store method and external reference (M-Pesa receipt number, bank
reference, cheque number), unique per tenant and method.
Links Documents reference their origin: invoice to sales order, goods receipt to purchase
order, payment to invoice, stock movement to source document.
Idempotency Every create request from POS, API or integration carries an idempotency key, so
retries never create duplicates.
History Changes to master data (prices, customer credit limits, supplier bank details,
employee pay) are kept as dated versions.

07 · ACCOUNTING ENGINE
Accounting engine
The ledger is double-entry. Operational modules never write journal lines directly; they
publish posted documents, and the posting engine converts them into balanced journal
entries using configurable posting rules.
Principles
Every journal entry balances: total debits equal total credits, enforced by a database constraint at
commit.
Every journal line carries company_id , branch_id , account, amount and a link to its source
document, so profit and loss can be reported per branch.
Posting happens in the same database transaction as the source document, so stock, payments
and books never disagree.
Posted entries are immutable. Corrections are reversing entries.
Sub-ledgers (customers, suppliers, inventory, M-Pesa clearing) must equal their control accounts.
A nightly job checks this and raises an exception if not.

Posting rules are data, not code: each maps a document type and line type to accounts, with defaults
from the chart of accounts template and per-company overrides.
Periods and closing
Periods are monthly. A soft-closed period accepts entries only from users with close permission; a
locked period accepts none. Back-dated documents into a closed period are rejected or redirected
to the current period, by policy.
Period close checklist: all branch days closed, reconciliations complete, sub-ledgers equal control
accounts, payroll posted, depreciation and accruals entered manually where needed.
Reports
Trial balance, profit and loss (by branch and consolidated), balance sheet, cash flow summary,
general ledger detail, customer and supplier ageing, VAT summary. Reports read from journal lines and
are reproducible for any past date.
Export to accounting software
Journal export by period in CSV and in formats importable by QuickBooks and Sage, with account
mapping per company, for businesses whose accountant keeps a separate system.

08 · INVENTORY ENGINE
Inventory engine
Stock is a ledger. Quantities are never edited directly; each change is an immutable
movement, and balances are derived from movements.
Stock movement record

stock_balance per location, product and batch is maintained in the same transaction as each
movement and can be rebuilt from movements at any time. A nightly job verifies they match.
Concurrency: balance rows are locked per product and location during posting to prevent double-selling the last unit.
Costing
Weighted average cost per product per company in 1.0. On each receipt: new average = (existing
value + receipt value) ÷ (existing quantity + receipt quantity).
Sales and outbound movements take the current average cost; the value posts to cost of goods
sold.
Landed costs (transport, duty) can be added to a receipt and spread across its lines before
averaging.
Batches and expiry
Products can be batch-tracked. Batch-tracked items pick first-expiry-first-out by default; the
cashier can override with a reason.
Expiry warnings are generated from batch quantities and dates.
Negative stock
A company policy. If allowed, the sale posts and an exception is raised for review; the cost is corrected
when stock arrives. If not allowed, the sale is blocked. Offline POS sales are always accepted and
reviewed after sync (section 09).

Transfers and counts
Transfer dispatch moves stock from source to an in-transit location; receipt moves it to the
destination. Differences on receipt require a reason and approval.
Stock counts take a snapshot at start. Movements during the count are tracked, so the variance is
calculated against the right expected figure. Variances above a threshold need approval before
posting.
09 · POINT OF SALE
Point of sale and offline operation
The POS must keep selling when the internet fails. It keeps a local copy of what it needs,
records sales locally, and synchronises when connected.
Device and session
Each POS device is registered to a branch and authenticated with a device credential plus the
cashier's login (PIN or password).
A till session is opened with a cash float and closed with a counted cash amount. Expected cash =
float + cash sales − cash refunds − cash paid out. The difference is recorded and, above tolerance,
raises an exception and a posting to till shortage or overage.
X report (mid-session summary) and Z report (session close) are produced per till session.
Offline design
Concern Approach
Local data Products, prices, tax codes, customers with credit status, cashier permissions
and current stock snapshot for the branch, in local SQLite. Refreshed
incrementally.
Recording sales Sales are written locally with a device-generated UUID and a local sequence
number, then queued for upload.
Numbering Each device has its own document series (e.g. POS-THK-02-000451 ), so offline
devices never collide.
Sync Uploads use idempotency keys; the server posts each sale exactly once, in
device order. Downloads apply changes since the last sync.
Conflicts Sales are facts and are always accepted. If a price, stock level or credit limit
changed while offline, the sale posts as recorded and an exception is raised for
review.
M-Pesa offline STK push needs connectivity. Offline, the cashier records the M-Pesa receipt
code shown on the customer's message; matching confirms it later.
eTIMS offline Sales are queued for eTIMS submission and submitted on reconnection, within
the period the eTIMS rules allow (section 11).

12 · PAYROLL
Payroll engine
Payroll runs monthly per company. Statutory rules are held in effective-dated rate tables,
not in code, because Kenyan rates and rules change.
Inputs
Employment terms (basic pay, allowances, benefits), versioned with effective dates.
Attendance, overtime and unpaid leave for the period.
Recurring and one-off earnings and deductions (advances, loans, SACCO, union dues).
Statutory rate tables: PAYE bands and reliefs, SHIF, NSSF tiers and limits, Affordable Housing Levy,
and any other statutory items in force.
Calculation pipeline
1 gross pay = basic + allowances + overtime + taxable benefits − unpaid leave
2 statutory pre-tax deductions (per rate tables, in the order the law sets)
3 taxable pay = gross − allowable deductions
4 PAYE = band calculation − reliefs
5 other statutory and voluntary deductions
6 net pay = gross − all deductions
7 employer costs = employer NSSF, employer Housing Levy, other employer items
Which deductions reduce taxable pay, and in what order, is part of the rate table definition, so a
change in law is a data change with an effective date.
Ziira Core 1.0 Technical Specification · Confidential Page 18
Run lifecycle
1. Create run for the period → calculate → review exceptions (new employees, pay changes, bank
changes, net pay below threshold).
2. Approve (approver cannot be the person who prepared the run, by policy).
3. Post to the ledger (section 07).
4. Pay: bank bulk payment file, or M-Pesa B2C where configured.
5. Outputs: payslips (PDF, sent by WhatsApp or email), P9 forms, and statutory return files for upload
to the relevant portals (KRA iTax, SHA, NSSF, Housing Levy).
Correctness: current rates must be confirmed from official sources at implementation and
whenever they change. Before launch, results are checked against a set of test employees
calculated independently by an accountant, covering every band and edge case.

Ziira Intelligence interface
Ziira Intelligence is a separate service that reads Core data, produces findings, and

systems through connectors that map their data to the same model.
Data flow
Core events (outbox) ─┐
Read replica ─────────┼─▶ Intelligence store (per-tenant analytical tables)
External connectors ──┘ │
├─▶ Checks engine ─▶ Findings ─▶ Command Center
├─▶ Baselines └▶ WhatsApp briefs and alerts
└─▶ AI layer (explain, rank, Ask Ziira)
Actions ◀── owner reply ── request via Core API (permission and approval checked by Core)
Components
Component Function
Canonical model A common schema for sales, payments, stock movements, documents, users and
branches. Core maps to it directly; connectors map Odoo, Zoho, QuickBooks and
others to it.
Checks engine Deterministic checks written as versioned SQL or code: reconciliation gaps, control
checks, thresholds. Each check has an ID, severity, scope and evidence query.
Baselines Per-tenant normal ranges (e.g. void rate per cashier, daily sales per branch and
weekday) computed from history, used to flag unusual values.
Findings store Each finding: check ID, entity, period, value, expected value, evidence record IDs,
severity, status (new, sent, acknowledged, explained, resolved, dismissed), owner.
AI layer Writes the plain-language explanation from the finding and its evidence; ranks
findings; answers questions by calling defined query tools, never by writing free SQL
against production.
Action requests Proposed actions (send reminder, draft PO, ask staff) are submitted to the Core API as
the requesting user, so Core's permissions and approval matrix apply.
Rules for the AI layer
Figures shown to users come from checks and queries, never generated by the model.
Ask Ziira answers are limited to the asking user's permissions and branch scope.
Every AI response stores the tools called and data used, for review.
Tenant data is not used to train external models; the AI provider's data terms must guarantee this.

APPENDIX A · DATABASE
Database schema
The complete PostgreSQL schema for Ziira Core 1.0: 11 schemas and 110 tables. It is
delivered as one migration per unit, generated from a single definition file so this
appendix and the SQL always match.
Schema rules
One PostgreSQL schema per unit: kernel , products , crm , inventory , payments , pos ,
purchasing , finance , people , command , and intel for the Ziira Intelligence store. Plugins get their
own schema named plg_<name> .
Foreign keys only to the kernel and to required modules. References to optional modules are
stored as plain IDs (soft references), so an optional module can be uninstalled without touching any
other schema.
Tenant isolation: every tenant table has tenant_id with row-level security forced on. The
application sets app.tenant_id per transaction; rows of other tenants are invisible and cannot be
written.
Immutable records: inventory.stock_movement , finance.journal_entry , finance.journal_line and
kernel.audit_log reject updates and deletes at database level.
Balanced journals: a deferred constraint trigger rejects any transaction that leaves a journal entry
unbalanced.
Reason codes enforced: stock adjustments, write-offs, count variances and voided sales cannot
be saved without a reason code.
Allowed values are check constraints on text columns, not database enum types, so units can
extend them in their own migrations.
